# infra/hosting — versioned copy of the real demo hosting gateway

This directory is a versioned, reviewable copy of the real local hosting gateway
configuration used for the demo's public-URL path: an nginx reverse proxy
(`mcp-gateway`) plus a cloudflared quick tunnel (`mcp-tunnel`) sitting in front
of the 32 per-pilot containers that `docker-compose.demo.yml` (repo root,
auto-generated by `scripts/release/generate_demo_compose.py`) already defines.

- `nginx.conf` — the gateway's nginx config. Verbatim copy of the real,
  operator-local `nginx.conf` used to run the demo.
- `compose.yaml` — the 32 pilot services plus `mcp-gateway` and `mcp-tunnel`
  (34 services total). Verbatim copy of the real, operator-local
  `compose.yaml`.
- `pilots.txt` — the 32 pilot identifiers (`family/platform`, one per line)
  that the gateway and compose file route for. Verbatim copy of the real,
  operator-local `pilots.txt`.

All three files were copied byte-for-byte from the operator-local path
`C:\Users\<operator>\.foss-mcp-tools\hosting\{nginx.conf,compose.yaml,pilots.txt}`.
They are not redesigned or "improved" here — this card versions the real,
known-working config as-is.

## Not wired into any automated deploy

This directory is documentation and a regression-tested snapshot, nothing
more. Nothing in this repository's CI, release, or deploy automation reads
from `infra/hosting/` yet. Actually redeploying the gateway/tunnel layer for
real still means copying these files to the operator-local hosting path and
running, there:

```
docker compose -p foss-mcp-hosting -f compose.yaml up -d
```

(per this project's own prior operating practice — see the public-hosting
notes referenced from `docs/DECISION_LOG.md`). A future card may wire this
into an automated path; until then, treat this directory as the versioned
source of truth for what the real config *is*, not as something that deploys
itself.

## Diagnostic note for RT4 (tail-latency root cause)

Three facts in the real `nginx.conf`, read directly (not inferred), directly
corroborate the round-2 audit's observed tail latency and matter for RT4's
eventual fix:

1. **`worker_processes 1;`** — nginx runs a single worker process. Every
   request across all 32 pilots is served by that one worker; there is no
   parallelism across OS cores for the gateway itself.
2. **`resolver 127.0.0.11 valid=10s ipv6=off;`** — the Docker embedded DNS
   resolver is queried with only a 10-second cache TTL. Because the upstream
   host in `proxy_pass` is a variable (see below), nginx cannot resolve it at
   config-load time and cache it indefinitely; it must re-resolve the
   upstream container name via DNS on a per-request basis once the 10-second
   TTL expires, adding a DNS round-trip to request latency instead of using a
   cached/keepalive upstream address.
3. **`proxy_pass http://mcp-$pilot:8080/$rest$is_args$args;`** — the upstream
   host (`mcp-$pilot`) is built from a variable captured from the request
   path (`$pilot`), not a static upstream name. A **variable `proxy_pass`**
   defeats nginx's upstream connection pooling/keepalive: nginx cannot
   pre-resolve or reuse a persistent connection to a target it only
   determines per-request, so every request pays the cost of a fresh
   upstream TCP connection (and, per point 2, often a fresh DNS lookup) rather
   than reusing a pooled one.

Together these three facts — one worker, per-request DNS re-resolution, and a
non-poolable variable `proxy_pass` — are real, directly-read evidence for why
the gateway adds tail latency under load, and should be the starting point
for RT4's fix (e.g., a static `upstream` block per pilot, or resolving pilots
to a fixed set of named upstreams at config-generation time) rather than
re-deriving the cause from scratch.
